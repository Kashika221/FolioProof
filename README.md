# FolioProof

**Multi-Source Professional Identity Fusion with Provenance**

Minor Project — Dept. of Information Technology, Maharaja Surajmal Institute of Technology.

FolioProof ingests a résumé, a GitHub profile, an optional LinkedIn export and an
optional cover letter, fuses them into one non-contradictory professional profile,
and generates a portfolio website in which **every generated sentence is traceable
back to the source span it came from**. Where sources disagree, a fixed
precedence order decides the winner.

The problem it solves is not "turn a résumé into a website" — that is a solved
problem. It is that the same person is described differently in four places, and
something has to decide which version is true.

---

## Which source feeds which section

| Section | Source |
|---|---|
| Experience, Education, Projects | **résumé only** — including each project's link |
| About | **LinkedIn summary** (voice) + cover letter + résumé facts |
| Skills | union of every source, with corroboration marked |
| Top Repositories, GitHub stats | GitHub |
| Gallery | **user uploads only** |

The gallery is deliberately upload-only. LinkedIn exposes no public API for post
media, a profile URL returns nothing without authentication, and scraping it
violates their User Agreement — so the only honest source is the person whose
portfolio it is. Images are stored per build and copied into `images/` on export.

## Export format

`GET /api/export/{id}` returns a zipped static site, not a single HTML blob:

```
index.html     the page, linking the two assets below
style.css      theme + per-section colour custom properties
script.js      navigation and provenance mode
images/        the uploaded gallery images
README.txt     how to view and where to deploy it
```

Drop the folder on Netlify, GitHub Pages, Vercel or Cloudflare Pages — no build
step, no server. `render_bundle()` produces the three text files;
`render_portfolio()` still exists for the in-app preview, where inlining is
what you want.

Experience, education and projects are résumé-only on purpose. LinkedIn exports
restate the same jobs in a different shape — `August 2025 - Present (1 year 1
month)` with no employer attached — which produced duplicated, half-empty
timeline rows. Conflict detection still runs across *all* sources, so a
disagreement is reported even though only the résumé's value ships.

## The About section

Generated by the LLM, **capped at 250 words**, deliberately non-technical, and
written in first person. Its inputs, in order of weight:

1. **LinkedIn summary** — the person's own "About" text, the only source where
   they describe *themselves* rather than list what they did. Its positioning
   is preserved.
2. **Cover letter** — motivation and direction.
3. **Résumé facts** — roles, projects, education, skills.

The prompt caps technology mentions at two or three for the whole passage; the
word limit is then enforced in code (`_cap_words`), because a prompt is a
request, not a guarantee.

## Model choice

`openai/gpt-oss-120b`, after Groq retired `llama-3.3-70b-versatile`.

Picked by benchmarking the live alternatives on a real CV rather than by
reputation:

| model | employers found | project links | verdict |
|---|---|---|---|
| `openai/gpt-oss-120b` | 3 / 3 | 3 / 3 | chosen |
| `openai/gpt-oss-20b` | 0 / 3 | 0 / 3 | returned no experience or projects |
| `qwen/qwen3.6-27b` | — | — | could not satisfy JSON mode |

Quotas are **per model**, so switching also moved the build onto a fresh daily
budget.

Requests were cut from ~9,150 to ~6,200 tokens at the same time: `max_tokens`
was reserving 6,000 for an output that is really ~2,000, and the JSON schema was
being pretty-printed on every call for no benefit. Both count against the
per-minute limit.

## One LLM call per build

The whole profile — structured facts *and* the written copy — comes back from a
single Groq call in `app/enhance/extract_all.py`, validated into one
`PortfolioContent` model.

It used to take 6–8: one per PDF source, one per project rewrite, one for the
About passage. That was ~130 s per build and exhausted the free tier's
100k-token daily budget in an afternoon. A single call is **~5 s**, and the
model sees every source at once instead of one project's evidence in isolation.

**Provenance survives it.** Span attachment happens *after* extraction —
`content_to_claims()` looks each value back up in the parsed PDF and binds its
bounding box — so the number of calls was never what made claims traceable. A
value that cannot be found in any source document is dropped, not published.

If the call fails — almost always an exhausted quota — the build returns
**503 with the reset time** (`Groq daily token limit reached for model
'…' — resets in 57m7s`) instead of saving a profile with no claims. An empty
build renders as "Your Name / Developer", which reads like a broken generator
rather than a quota that clears on its own.

**Conflict detection survives it too**, by a different route. With the sources
merged into one call, LinkedIn's competing value never becomes its own claim, so
the model reports disagreements explicitly in `discrepancies[]`. Both sides must
still anchor to real document lines or the discrepancy is discarded — the
model's word alone is not evidence.

## Projects and GitHub are not matched

A project displays the link **the résumé itself gave** — a live demo or a repo
URL. FolioProof does not try to pair résumé projects with GitHub repositories.

That matching used to exist and it was guesswork: `VeriFy: Authenticity
Validator for Academia` and `Academic_Validattor_SIH` are the same project but
share almost no tokens, while a name like `VIO` matches half a dozen unrelated
repos. Repositories now get their own **Top Repositories** section instead of
being forced into pairs.

## Source precedence

When two sources state different facts, the more authoritative one wins:

```
resume  >  linkedin  >  github  >  cover_letter
```

- **resume** — curated per application; the most deliberate statement of fact.
- **linkedin** — maintained, but usually staler and edited less carefully.
- **github** — produced by tooling. Repo names and language stats are facts
  about code, not claims the candidate wrote about themselves.
- **cover_letter** — narrative and tone, not a record of dates or titles.

One deliberate exception, in `GITHUB_AUTHORITATIVE_FIELDS`: GitHub keeps the
facts only GitHub can know — stars, forks, repo URL, language breakdown. A
résumé cannot out-rank GitHub on a star count.

Conflicts are detected **and resolved automatically**, so a build is never
blocked waiting for input. The UI marks the winning option `highest priority`
and lets you override it.

Implemented in `app/fusion/priority.py`; applied in claim merging
(`merge_by_priority`), skill fusion, project fusion and conflict resolution.

## The core invariant

`app/models/claims.py` declares:

```python
class Claim(BaseModel):
    kind: ClaimKind
    value: str
    evidence: list[Evidence] = Field(min_length=1)   # <- the whole guarantee
```

A claim with no evidence **cannot be constructed** — Pydantic rejects it. Every
downstream stage operates on `Claim` objects, so a fact with no source has no
representable form anywhere in the pipeline. Enforced by the type system, not by
a prompt.

## Why pdfplumber, not PyPDF2

pdfplumber returns **word-level bounding boxes**. Those coordinates survive all
the way to the rendered page, which is what makes the provenance viewer
possible: hover any sentence and the exact rectangle on the original PDF that
supports it is highlighted.

## Pipeline

```
  résumé.pdf ─┐
 linkedin.pdf ─┤─> pdfplumber ──> lines + bboxes ──┐
cover_letter ─┘                                    │
                                                   ├──> Claims (evidence-bound)
  github user ───> REST/GraphQL ──> repos+READMEs ─┘
                                                   │
                          ┌────────────────────────┘
                          v
              ONE Groq call -> PortfolioContent
         (facts + About + hero + reported discrepancies)
                          │
                          v
            bind every value back to its source span
                          │
                          v
       skill canonicalisation + SOURCE PRECEDENCE merge
         (resume > linkedin > github > cover_letter)
                          │
                          ├──> conflicts   auto-resolved, user can override
                          v
          portfolio HTML — 4 themes, per-section colours,
                 data-provenance on every sentence
                          │
                          v
                      MongoDB
```

## Setup

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
```

Copy `backend/.env.example` to `backend/.env` and fill in:

- `GROQ_API_KEY` — free key from <https://console.groq.com/keys>. Required:
  without it a build fails with a clear error rather than producing an empty
  page. One build is a single call of roughly 6k tokens.
- `GROQ_MODEL` — defaults to `openai/gpt-oss-120b`.
- `GITHUB_TOKEN` — optional. Unauthenticated GitHub allows 60 requests/hour;
  a token raises it to 5,000.
- `MONGODB_URI` — see Storage below.

Run:

```bash
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8000 --app-dir backend
```

```bash
npm --prefix frontend run dev
```

Tests:

```bash
.venv/Scripts/python.exe -m pytest -q backend
```

Fixtures (regenerate if you change them):

```bash
.venv/Scripts/python.exe backend/tests/make_sample_resume.py
```

```bash
.venv/Scripts/python.exe backend/tests/make_sample_linkedin.py
```

`sample_linkedin.pdf` deliberately contradicts the résumé's graduation year so
the precedence test has something real to resolve.

## Storage

Profiles live in **MongoDB** — one document per build, the `ProfileGraph` dumped
straight to JSON. A document store fits because a profile is a deeply nested
tree of claims carrying variable-shaped locators; flattening that into
relational tables would buy nothing.

```bash
MONGODB_URI=mongodb://localhost:27017                        # local server
MONGODB_URI=mongodb+srv://user:pass@cluster.mongodb.net/     # Atlas free tier
MONGODB_DB=folioproof
```

If no server is reachable, `ProfileRepository` logs a warning and falls back to
JSON files under `backend/data/cache/profiles/` so the app still runs.
`GET /health` reports which backend is live (`mongodb` or `json-files`).

Indexes created on connect: unique `build_id`, plus `created_at` for listing.

## Themes

Four themes — **Minimal**, **Playful**, **Developer Terminal**,
**Academic** — each with per-section colour customisation across all eleven
sections (hero, about, skills, projects, repositories, experience, education,
github, gallery, achievements, contact).

This composes rather than multiplies because the renderer never writes a literal
colour into a rule. Each section reads its palette from scoped custom
properties:

```css
[data-section="projects"] { --bg: …; --fg: …; --accent: …; --muted: …; }
```

A user override is just a different set of variables for one section — no layout
code is duplicated across 4 themes × 11 sections.

**Playful** (coral `#ff6b6b`, teal `#4ecdc4`, yellow `#ffe66d` on `#fff5f5`)
rotates its three brand colours through the per-section accent, so scrolling
cycles hues instead of repeating one. Its floating shapes are `::before` /
`::after` pseudo-elements on `.section` rather than extra markup — that keeps a
theme a pure stylesheet swap, with no template branch and no stray DOM in the
other three themes.

Profiles saved under the old `glass` key still load; `LEGACY_THEME_KEYS` maps
them to `playful`.

### Provenance viewer

PDF pages are rasterised server-side by `pypdfium2` and served from
`/api/profile/{id}/page/{source}/{page}`. Evidence boxes are positioned in
**percentages of the PDF page size**, not pixels, so the overlay stays aligned
at any image scale or container width.

## Evaluation metrics

`build_profile()` returns these on every run:

- **entity-resolution accuracy** — precision/recall/F1 on résumé↔GitHub matching
  against a hand-labelled set.
- **conflicts detected / auto-resolved** — cross-source contradictions found and
  settled by precedence.
- **multi-source corroboration** — claims backed by more than one source.
- **latency** — end-to-end seconds per profile.
